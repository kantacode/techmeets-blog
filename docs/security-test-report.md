## セキュリティテストレポート（Week 8 練習課題2）

### テストの方法

次の2つの方法で確認しました。

1. **実際のアプリへの手動テスト**：Docker で動いているアプリ（http://localhost）に、`curl` で攻撃用のリクエストを送り、結果を確認した
2. **自動テスト**：`src/tests/Feature/SecurityTest.php` に10件のテストを書いた。次のコマンドで、いつでも同じ確認をやり直せる

```bash
docker compose exec app php artisan test --filter=SecurityTest
```

### 結果まとめ

| # | 項目 | 試した方法 | 期待する結果 | 結果 |
|---|---|---|---|---|
| 1 | XSS（投稿） | タイトルに `<script>alert("title")</script>`、本文に `<img src=x onerror=alert(1)>` を入れた投稿を表示 | スクリプトが実行されず、文字として表示される | ✅ `&lt;script&gt;` に変換されて表示された |
| 2 | XSS（コメント・ユーザー名） | コメントに `<script>`、ユーザー名に `<b>` を入れて表示 | 同上 | ✅ どちらも変換されて表示された |
| 3 | CSRF | トークン（`_token`）を付けずに `POST /login`・`POST /posts` を送信 | 419 エラーで拒否される | ✅ 419 で拒否され、投稿も作られなかった |
| 4 | SQL インジェクション（ログイン） | メール・パスワード欄に `' OR '1'='1` を入力してログイン | ログインできない | ✅ 入力エラーになり、ログインできなかった |
| 5 | SQL インジェクション（URL） | `/posts/1' OR 1=1--` にアクセス | 404 になる | ✅ 404 になった |
| 6 | 認証（ログイン必須） | 未ログインで `/posts/create`・`POST /posts`・コメント送信・`/dashboard` にアクセス | ログイン画面へ移動させられる | ✅ すべて `/login` へリダイレクトされた |
| 7 | 認可（投稿） | ユーザー B で、ユーザー A の投稿の編集画面・更新・削除を実行 | 403 で拒否される | ✅ すべて 403。投稿の内容も変わらなかった |
| 8 | 認可（コメント） | ユーザー B で、ユーザー A のコメントを削除 | 403 で拒否される | ✅ 403。コメントは残った |
| 9 | なりすまし投稿（マスアサインメント） | 投稿フォームに他人の `user_id` を紛れ込ませて送信 | 自分の投稿として保存される | ✅ ログイン中のユーザーの ID で保存された |
| 10 | パスワードの保存 | 会員登録後、DB の `password` 列を確認 | 元のパスワードではなくハッシュ値で保存される | ✅ `$2y$...`（bcrypt、60文字）で保存されていた |
| 11 | 総当たり攻撃 | 間違ったパスワードで6回連続ログイン | 一定回数で止められる | ✅ 6回目で「Too many login attempts」と表示され、しばらくログインできなくなった |
| 12 | 機密情報の管理 | `git ls-files` で `.env` がコミットされていないか確認 | `.env` は Git に含まれない | ✅ ルートの `.env` も `src/.env` も `.gitignore` で除外されていた |

### 対策の内容

| 攻撃 | このアプリでの対策 |
|---|---|
| XSS | 表示はすべて Blade の `{{ }}` を使用。改行表示のための `{!! !!}` も、中で `e()` を使って先に変換している |
| CSRF | すべてのフォームに `@csrf` を入れている |
| SQL インジェクション | DB 操作はすべて Eloquent を使い、SQL を文字列でつなげていない |
| 認証 | 投稿の作成・編集・削除と、コメントの書き込み・削除のルートを `auth` ミドルウェアで保護 |
| 認可 | 投稿とコメントの編集・削除で、`user_id` とログイン中のユーザーの ID を比べ、違えば `abort(403)` |
| なりすまし | `user_id` はフォームの値を使わず、コントローラーで `auth()->id()` を入れている |
| パスワード | Breeze の User モデルが自動でハッシュ化（bcrypt） |
| 総当たり | Breeze のログイン処理に、5回失敗で一時停止する制限が入っている |

### わかったこと・今後の課題

- テストした12項目すべてで、攻撃を防げていることを確認できた
- 本人チェック（`if ($post->user_id !== auth()->id())`）を、`edit`・`update`・`destroy` の3か所に同じように書いている。Week 9 の Policy を使えば、1か所にまとめられそう
- 商品管理（/products）は、まだログインしなくても登録・編集・削除できる。今回の課題の範囲外だが、実際に公開するならログイン必須にするべき
